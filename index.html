How LLM Tokenization Works (and Why Words Don't Equal Tokens)

Language models do not read characters or space-separated words directly. Before inference, text passes through a subword tokenizer—typically Byte-Pair Encoding (BPE)—which maps frequent byte sequences to integer IDs.

For standard English prose, one token averages roughly 4 characters or 0.75 words. That ratio breaks down quickly in real engineering workloads:

  • JSON and code syntax: Brackets, quotes, colons, indentation, and camelCase identifiers split into extra tokens. Pretty-printed JSON with 4-space indentation can cost 20%–35% more input tokens than minified JSON.
  • Numbers and IDs: UUIDs, timestamps, and base64 strings rarely appear in merge tables, often consuming 1 token per 1–3 characters.
  • Non-Latin scripts: CJK characters, Cyrillic, and emojis frequently encode as multiple UTF-8 bytes per character, increasing token density compared to English.

Batch API vs. Real-Time Endpoints: When to Switch

Running every LLM call through synchronous endpoints is one of the fastest ways to inflate an inference bill. Most major providers offer an asynchronous Batch API with a 50% discount on both input and output tokens in exchange for a 24-hour completion SLA.

  • Use real-time endpoints for interactive chat, autocomplete, live agent tool calls, and anything blocking a user-facing HTTP request.
  • Use Batch APIs for offline document extraction, nightly summarization, dataset labeling, RAG chunk enrichment, and automated prompt evaluation suites.
  • Pair with prompt caching when thousands of requests share the same long system prompt, tool schema, or reference document—cutting repeated input token costs by 50% to 75% or more.

Frequently Asked Questions

How accurate is a client-side LLM prompt token counter?
Client-side BPE heuristics are typically within 3% to 8% of exact provider tokenizers (such as OpenAI's o200k_base / cl100k_base or Anthropic's tokenizer) for English prose and standard JSON. Exact counts differ slightly across providers because each model family ships a different vocabulary size and merge table. For strict billing audits, verify against your provider's official token-counting endpoint.
Does the context window limit include both input and output tokens?
Yes. The context window covers the combined total of your system prompt, tool definitions, conversation history, user input, and the model's generated output tokens (including internal reasoning tokens on reasoning models). If input + output exceeds the model's limit, the API will return a context length error or truncate the response.
Why are output tokens more expensive than input tokens?
Input tokens are processed in parallel during the prefill stage, which saturates GPU compute efficiently. Output tokens are generated sequentially—one token per forward pass—which is memory-bandwidth bound and keeps the KV-cache allocated in VRAM for the entire generation. Providers price output tokens 3x to 5x higher to reflect that hardware bottleneck.
Can Batch API discounts and prompt caching be combined?
Stacking rules vary by provider. Anthropic and Google Gemini support combining prompt caching with Batch API pricing on eligible models, whereas OpenAI's Batch API provides a flat 50% discount off standard rates with automatic caching behavior that depends on request timing. Use the toggles above to model both scenarios and confirm current billing rules in your provider's docs.
Is my prompt text sent to any server when using this calculator?
No. TokenMeter runs 100% locally in your browser using vanilla JavaScript. No prompt text, token counts, or pricing configurations are transmitted to any backend or third-party analytics service.
